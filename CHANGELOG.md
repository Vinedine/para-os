# Changelog

Template revisions. Each vault's `CLAUDE.md` carries the revision it was last aligned to, as an HTML comment on line 3:

```
<!-- para-os-template: 2026.08.01 -->
```

`/para-upgrade` reads that marker, compares it against the master's, and applies the entries below that fall between the two. A vault with **no marker** predates the scheme: treat it as pre-2026.08.01 and run the full 2026.08.01 entry against it.

Revisions are dated `YYYY.MM.NN`, not semver: the year and month it shipped, then a zero-padded sequence for the nth revision of that month. The sequence counts, it doesn't grade - `2026.08.02` is not a patch on `2026.08.01`, only the one after it. A revision marks "the template changed in a way an existing vault has to react to"; wording tweaks that change no rule don't get one. Every comparison in the scheme is a plain string compare, which is what the padding is for.

**One legacy label.** The first revision shipped as `2026.08`, before the sequence existed, and was renumbered to `2026.08.01` in `2026.08.02`. A vault still stamped `2026.08` is already on `2026.08.01`: read it as that label, collect the entries after it, and restamp it. Never re-run the `2026.08.01` entry against it.

Installed [integration](integrations/) scripts share the scheme. Each shipped script carries its own marker in its header, stamped with the revision that script last changed in:

```
para-os-integration: granola 2026.08.02
```

An entry's **Integrations** line says which ones moved and why. That marker is read per script, independently of the vault's template marker, so a vault already on the current revision can still be told its installed copy is behind.

## 2026.09.02

Most of these are silent failures found by running the skills and scripts against real vaults rather than by reading them: each reported something confidently wrong instead of failing, which is why none had surfaced before. Each entry ends with its reaction.

**The activity ledger now records what a script wrote and what a session did.** `activity.py` gains two fields. `touched` lists the vault files whose mtime moved while a tool ran, for tools that neither name their own path (`Write`, `Edit`) nor are unable to write (`Read`, `Grep`, ...), capped at `touched_max_files` with the uncapped count in `touched_total`. Without it a script run through Bash left no trace beyond its interpreter's name, and in one real vault 52 of 63 changed files had no write event anywhere. It is inferred, not observed: its window is the tool's duration plus `touched_slack_ms`, so a file another person's sync client landed in that window is indistinguishable from one this call wrote, and `/para-activity-review` is told never to name a person as the author of a `touched` path. `SessionEnd` gains a `summary` object (`prompts` per `prompt_id`, `tools`, `writes` with `touched` counted, `failures`, `denials`, `duration_s`, `last_prompt_tools`), because `reason` belongs to the harness and a client may report `other` for every ending. `summary.prompts: 0` separates sessions nobody typed into, which in one real vault were 72% of the files, from sessions anyone worked in. Both fields are opt-out (`record_touched`, `record_summary`); nothing backfills an older ledger, and the skill's `signals.md` describes such a window as blind rather than quiet. Reaction: re-sync `activity.py` and restamp its marker; re-sync installed `/para-activity-review` copies.

**`/para-triage` checked whether `triage/` was empty before the step that fills it.** Step 1 stopped on an empty folder, and Step 2 is what runs the sync-script sources that write into it, so a vault with a declared source could report clean while the source sat unread. Step 1 now only verifies the vault root; the emptiness check moved to the end of Step 2, after the source pull and the loose-file listing. `convert` had the same bug and is fixed by the same move. Reaction: re-sync installed skill copies, global installs and vault-bundled `.claude/skills/` alike.

**`/para-triage` approved every deletion on one word, which its own shared discipline forbids.** `operating-discipline.md` has required individual approval for deletions since 2026.08.03; Step 6 asked for one `go` against a table. Steps 5 and 6 are now one step: a manifest (one line per question) prints first, then each item or linked group is its own `AskUserQuestion`, four to a call, the proposal first and labelled `(Recommended)`, with the reasoning in the option description and an escape on every question that files nothing. Grouping has three limits: never a delete with anything, never differing destinations, never more than five. An unanswered question (`[No preference]`) is a deferral, re-asked once and then recorded, never assent. The vocabulary gains **Delete (no lasting value)** for a note whose outcome is already recorded elsewhere, under a rule that filing is not the default. The table survives on every path with nobody to ask (`preview`, `apply`, `convert`, a scheduled run) and on a new `table` argument; the standing rule is fail toward the table. Reaction: re-sync installed skill copies; the skill gains `references/approval.md`. No vault changes and no marker moves.

**The same batched approval was in four more skills, and the mechanics now live in `para-shared/asking.md`.** `/para-activity-review` offered to delete consumed ledger files on one yes; `/para-deep-clean` had the per-item rule and no mechanism, every finding going onto one table; `/para-archive` asked per open action in prose and took one answer for all. The shared file holds what every caller does identically (manifest, four questions a call, question shape, grouping limits, reading an Other or a skipped answer, when not to ask); each skill keeps only its vocabulary. Two scope rules: `/para-deep-clean` asks only where approving loses something (a close, a stripped date marker, a delete), while lossless demotions still batch onto the table and the 20-item gate offers the table when a batch is large; `/para-archive` collapses "survives" and "where to" into one question naming the destination file. The recommended option is the one that changes nothing only where the loss would be irreversible; elsewhere it is what the evidence supports, because a systematically safe recommendation stops being read. `/para-new` adopts the pattern for the opposite reason: the sorting test is now asked wherever more than one shape is defensible, each option carrying its row of the test and a `preview` of the scaffold it would produce, while the interview that follows stays free text. A preview shows content as it will be written, never a prettier rendering. Reaction: re-sync installed skill copies; every adopting skill gains `AskUserQuestion` in `allowed-tools`, without which it silently falls back to prose. No vault changes.

**Two rules the adoption forced.** `/para-archive` skips Step 2 for an idea, which carries no `actions.md` by the vault's own rule, so its routing questions only ever fire for a project that finished while its `actions.md` fell behind. And a `preview` on any skill that now asks prints the manifest before the table, so it still shows the shape of the run it stands in for (how many questions, which items group, how many rounds) without asking; the mechanics are in `asking.md`.

**`outlook.py fetch` grouped nothing and read everything.** A record was one message, so a thread was judged once per message (137 routing decisions over 68 threads on one live mailbox). `fetch` now groups by `conversationId`, falling back to the message id where Graph omits it; a record describes the newest message and gains `message_count`, `messages` (newest first) and `participants` (everyone who wrote, minus the owner), and stderr reports messages and threads both. It also read `/me/messages`, which is every folder, so Junk, Deleted Items and Sent came back as candidates: on two live mailboxes over two days, 171 of 233 messages came from those folders. It now reads an allowlist, `FETCH_FOLDERS = ("inbox", "archive")`, by Graph's language-independent well-known names; a missing folder is skipped. `search` still reads the whole mailbox. Bulk mail is dropped on the RFC 2369 `List-Unsubscribe` header and nothing else (`--include-bulk` keeps it); there is deliberately no noreply-style sender backstop, which `para-shared/connectors.md` forbids. Reaction: straight file copy. A caller reading `subject`, `from`, `received`, `preview` or `link` needs no change; one that counted records was counting messages and now counts threads, and the candidate count on a busy Junk folder drops sharply.

**OAuth scope is per account, and a failed token exchange says why.** `Mail.Read.Shared` had gone in as one module-wide constant, and the token endpoint refuses a refresh that asks for more than was consented (`AADSTS65001`), so every work mailbox on a machine stopped authenticating while personal ones, whose endpoint drops the extra silently, kept working. `account_scope()` now asks for it only on an account some entry names as its `via` or that carries `shared: true` (set by `login --shared`, for consenting a user before the shared entry exists). A failed `access_token` now quotes Microsoft's `error_description` and gives the remedy the `AADSTS` code implies; the description parser no longer raises on a response without one. Reaction: none for an existing account, whose narrow refresh succeeds on its own. Add delegated `Mail.Read.Shared` to a tenant app only where it reads a shared mailbox.

**`login` is a browser sign-in now.** Security defaults block device code flow, and from 1 July 2026 that is the shipped default on every new Entra tenant, enforced after a 24-hour grace period, so a fresh tenant works for a day and dies the next afternoon. `login` runs authorization code + PKCE on a loopback redirect; `login --device-code` keeps the old flow. Nothing recorded in a refresh token says which flow minted it, so no existing account needs a re-login. Reaction: register `http://localhost` (Mobile and desktop applications platform, no port) as a redirect URI on every app this reaches, or its next `login` falls back to `--device-code`.

**Work state in a root README is banned as a category, not by syntax.** The rule listed five shapes and a vault kept all five out while carrying open questions as italic sentences, one of them already answered on a contact card the README never linked. It now names prose (_to confirm_, _still to settle_) as one of the syntaxes. Reaction: move any such sentence out of the root README to the file that owns the fact, or resolve it.

**`/para-deep-clean` reads contact cards.** Phase 1 gains an uncited-contacts scan (a person with a card, named without a link, often with the card's details inline), a same-number-two-values check, and a flag for a figure with no as-of date or a projection among facts. Phase 3.5 now reads every contact card and area README unconditionally, since a small file trips no growth signal, and gains **contradictions** as a finding kind, resolved by naming the owning file and checking a source document, never by trusting the last-edited copy. Phase 4 verifies both. Reaction: re-sync installed skill copies.

**`/para-daily-brief <entity>` scopes the brief to one project or area.** The four scope words are reserved; anything else resolves to exactly one `projects/` or `areas/` folder (exact, then unique substring, else ask; never guess, never widen to the vault). It renders every open item by bucket, uncapped, with the entity's own health flags and a next action; it does not read `brief.md`. A second grep renders items about the entity filed elsewhere (a contact file, `areas/business/`) as `🔗 Mentioned elsewhere`, never in the entity's totals. Reaction: re-sync installed skill copies.

**`multi-vault/`: an optional layer for several vaults on the same inboxes.** A registry outside every vault (`vaults.json`, from the shipped template) and `/para-ingest`, which reads each declared source once, decides only which vault an item belongs to, and stages a note in that vault's `triage/`. It ships as a module, not in `base/.claude/skills/`, so a single-vault adopter carries no frontmatter for it. The connector fetch protocol moved to `para-shared/connectors.md`, shared by both callers; judging stays in `/para-triage`'s `sources.md`. `/para-triage` defers its own pull only when the registry lists the vault as active **and** a run log from the last 48 hours exists, and says which in its summary. `tools/check.py` walks the module under the same skill contract. Reaction: none for a single-vault adopter beyond re-syncing `/para-triage`, whose deferral clause falls back to a local pull where there is no registry. An operator with several vaults copies `vaults.json.template` outside the vaults, fills it in, and installs `/para-ingest` and `para-shared/connectors.md` beside the bundled skills.

**A ledger keyed on a thread turned one disposition into a permanent dismissal.** Both `/para-ingest`'s staging ledger and `/para-triage`'s seen-ledger dropped every later message on a dispositioned thread. Every entry now carries `seen_through` (the RFC822 `Message-ID` of the newest message at disposition) and `seen_date`; step 5 of `connectors.md` makes a cheap date cut and step 6 settles it against the true message list. A resurfaced thread stages a fresh note holding only what arrived past the watermark, names the earlier disposition, and is routed from scratch; where the note's computed filename exists, ` 2` is appended. An entry without the pair is read as watermarked at its `date`. Reaction: re-sync installed `/para-triage`, `para-shared/` and, where installed, `/para-ingest` copies. No ledger needs migrating.

**The template ships as rules only.** `base/CLAUDE.md.template` went from 148 to 117 lines with every heading unchanged; the rationale it carried is derivable and stays at the 2026.09.01 ref. The flavor skeleton and the example vault condensed the same way, and `## Do not add` gains "procedure and rationale in this file", with the file staying under 200 lines. `tools/check.py` caps every `.template` at 120 lines and the example vault at 200. Reaction: **this is the one revision where `/para-upgrade` condenses.** It replaces the vault's copy of each invariant section (PARA layout, Lifecycle, Archive hygiene, Actions and its subsections, Filing and naming, Authoritative sources, Language, Memory, File formats, Integration scripts and their state, Do not add; plus `iPad access and rendering` for a vault declaring `readonly-ipad`, whose skeleton is its master) with the template's shorter text, carrying forward only the vault's own departures. The vault's own sections are out of scope and stay.

**`/para-deep-clean`'s revision precondition read the working tree and presumed a clone.** During any unshipped revision every vault read as behind, and `/para-upgrade` refuses uncommitted refs, so the two skills pointed at each other. It now reads the master's marker the way `/para-upgrade` does, `git show <ref>:base/CLAUDE.md.template` at a committed ref defaulting to `origin/main`; an in-flight revision is one line, not a vault defect. A missing clone is a caveat on the report rather than a stop, since nothing in the audit depends on the master. Reaction: re-sync installed skill copies.

**Integrations.** Updated: `activity` to 2026.09.02 (`touched`, `summary`); `outlook` to 2026.09.02 (`fetch` groups by conversation, reads inbox and archive, resolves scope per account, explains a failed token exchange, signs in through the browser). Unchanged: `granola` stays at 2026.09.01. Reaction: straight file copy for both, then restamp the marker in each installed copy.

## 2026.09.01

Eight changes, five of them a silent failure found in the field.

**Every triage file the outlook connector has ever written is a 255-character preview, not the mail.** `fetch_messages` and `search_messages` selected `bodyPreview`, and `write_triage` wrote that straight into the file. Graph caps `bodyPreview` at 255 characters, so every record this integration has produced, in every vault, holds a body cut off mid-sentence - with no ellipsis, no marker, and a header that reads as a complete record. That last part is what makes it worse than a loud failure: a truncated record that announces itself is a nuisance, one that presents as complete gets quoted, summarised and built on. Found when a source record of an eight-message thread turned out to hold five messages, each cut at 255 characters, one of them a set of in-line answers to five questions of which the preview captured the opening line and the signature. Filing now calls a new `fetch_body()`: a single-message `GET /me/messages/{id}?$select=body,uniqueBody` with `Prefer: outlook.body-content-type="text"`, so Graph does the HTML-to-text conversion server-side and nothing here parses HTML. `uniqueBody` first - the reply *without* the quoted history, so the fifth message in a thread is not five copies of the thread - with `body` as the fallback when Graph cannot work out the boundary and `bodyPreview` as the last resort, and a failed fetch warns and falls back rather than killing the sync. Deliberately a second round trip rather than another `$select` on the collection: `uniqueBody` is not returned on collection queries at all, and `body` on a collection would drag whole quoted threads through every page of a sync for messages that mostly will not pass the filter. It runs only for messages actually being written, so dry runs and the listing stay as cheap as before. **Filtering still reads `bodyPreview`, and that is correct** - 255 characters is plenty for a keyword hypothesis - so the script docstring and the README now separate FILTERING from FILING in as many words, because conflating them is how this was written in the first place. Reaction, and it is the one that costs real time: re-sync the script, then treat every triage-derived record filed before this revision as a preview. The fix does not repair what is already on disk, and nothing in those files marks them. Anything you have since built on - a brief, a summary, a decision - wants the mail read again.

**A forwarded message was filed without the thing it was forwarding.** The `uniqueBody`-first ordering above is right for a reply and backwards for a forward, and the same revision that introduced it needed a second pass to say so. Graph's `uniqueBody` excludes whatever it considers quoted; for a `Fwd:` the entire forwarded message is the quoted part, so what reaches the triage file is the covering note alone - or nothing at all, for a forward sent without one. A sync filed two `Fwd:` offers cut off immediately after the literal line `Begin forwarded message:`, with the covering note and the offer itself both missing, while a `bodyPreview` search proved the content was there to be had. Same failure class as the bug above, and worth stating plainly: fixing a truncation bug is where a *new* truncation bug is most likely to be introduced. A new `is_forward(subject)` reads the whole leading `XX:` chain and asks whether any token in it is a forward marker - `Fwd:`/`FW:`, and the equivalents other clients write (`TR:`, `WG:`, `Doorst:`, `RV:`, `ENC:`, `VS:`, `VB:`, `I:`). The reply half is deliberately not enumerated: any non-forward token is stepped over, so `AW:` or `Antw:` on top of a forward needs no list to handle. The marker list leans inclusive because the two errors are not equal - missing a forward loses the forwarded message silently, while mistaking a reply for one merely files its quoted thread; `fetch_body` tries `body` before `uniqueBody` for a forward, and keeps the existing order for everything else. The subject is the only signal available before the body is fetched, which is why it decides. Reaction: none beyond re-syncing the script - but a `Fwd:` filed by an earlier copy is truncated the same way a pre-2026.09.01 record is, and for the same reason nothing in the file says so.

**A keyword that doubles as somebody's home address matched every parcel notification forever.** `match_body` is a per-account switch, so the only way to stop a street name matching the *bodies* of courier and marketing mail was to turn body matching off for the whole mailbox - which reinstates, for every other keyword on that account, exactly the silent-drop blind spot `match_body` exists to close. Nothing narrower existed: the filter matches contacts, `match_all`, or keywords, with no sender or domain exclusion to reach for instead. This is not an edge case for a property vault, where a keyword is a street: the same address a tenant's parcels are delivered to is the one the vault tracks. A new **`subject_only_keywords`** names the keywords that skip the body loop and are checked against the subject only, resolving vault-level or per account with the same independent fallback as the other three settings, while every other keyword on the same account keeps matching subject and body. The `sync` scope line reports the count - `10 keywords (subject+body, 1 subject-only)` - because with an opt-out that now resolves per keyword as well as per account, which filter ran against a mailbox stops being answerable from the config at a glance. Reaction: re-sync the script; the setting is optional and a config that omits it behaves exactly as before.

**A vault fed by more than one mailbox could not sync at all, on anybody's machine.** `cmd_sync` checked every account in `outlook.config.json` against this machine's local secrets and hard-exited on the first one not logged in here, before syncing anything, including the accounts that were fine. A refresh token lives only on the machine it was granted on - that is `account_app`'s own design, not an accident - so on a vault with two or more mailboxes **no machine ever holds every account**, not even the machine of whoever added the second one. The result was a permanent failure for the whole team the moment a vault grew past one mailbox, with an error naming an account the reader cannot log in and no hint that `--account` was the way through. A plain `sync` now filters out the accounts that are not logged in here, warns one line per skip on stderr, and proceeds with what is present, exiting only when *none* of the vault's accounts are available. `--account <email>` still hard-exits on a named account that is not logged in, because a direct ask deserves a direct answer rather than a silent skip. No config schema change. Reaction: none beyond re-syncing the script. A single-mailbox vault behaves exactly as before.

**A granola route target that names a folder is wrong on every machine but one.** `route` in `granola.config.json` maps a title prefix to a **vault folder name**, and `resolveDest` compared that value against `path.basename(VAULT_ROOT)` as an exact string. For a vault synced from SharePoint that comparison is unsound: the OneDrive client names a synced library in **its own display language**, so one library is `Client Site - Documents` on an English machine and `Client Site - Documenten` on a Dutch one, while `granola.config.json` is version-controlled and syncs to every member. A literal name is therefore correct for at most one language group - and the failure mode is the bad one, the same class as the `bodyPreview` bug above and unnoticed for the same reason: a non-matching target returns `{skip: true}`, which the reporting loop handles with a bare `continue` and no output at all, not `UNROUTED`, not a count, so the meeting is dropped and the run still reports success. Three changes. A route value of **`"."` means "the vault this copy lives in"**, so no config ever has to name a machine-local folder; it is the third routing shape, and the one a client-tenant vault needs, since single-vault mode takes *every* meeting and would file other clients' calls into a shared client library. One join serves this vault and every sibling, since the parent plus this vault's own name *is* its root and a rename moves both together. An unresolvable route target now **warns once at startup** instead of vanishing per meeting - a warning rather than an exit, since a sibling vault may legitimately not be synced on a given machine. A `--vault` naming something no route points to **exits**, because a target typed on the command line is an explicit ask and cannot be explained by an unsynced sibling; in single-vault mode, where the flag is inert, it says so. And the closing summary gains a `· other vaults: N`, so the line adds up to the meeting count in the header: the skip stays silent per meeting, because naming another vault's meetings one by one is noise, but a run that dropped every meeting no longer prints the same three zeroes as a run that genuinely had nothing to do. Reaction: re-sync the script, then change any route value naming this vault's own folder to `"."`. Sibling routing by name is unchanged and still correct: a sibling's folder name is one you chose, not one a sync client translated.

**The activity hooks stop logging the moment a session changes directory.** The install snippet wired every hook as a bare relative path, `py resources/scripts/activity.py`, on the stated assumption that hooks run with the vault folder as their working directory. They do not: a hook inherits the calling session's working directory, and that directory moves - a `cd` inside one Bash tool call persists for the rest of the session, so from that point every hook invocation fails to locate the script (`can't open file ... No such file or directory`) until something `cd`s back. Nothing surfaces it. The ledger simply stops, and a usage review reads the silence as an idle session rather than a broken hook, which is the worst possible reading for a tool whose primary signal is absence. All seven hook commands are now anchored to `$CLAUDE_PROJECT_DIR`, quoted, because a vault path usually contains spaces. `activity.py` itself is unchanged and keeps its `2026.08.03` marker - the defect was in the install instructions, and bumping a script marker over a README fix would report drift on copies that are byte-identical. Reaction: edit the seven hook commands in the vault's `.claude/settings.json` to `py "$CLAUDE_PROJECT_DIR/resources/scripts/activity.py"`. Nothing else changes, and past gaps in the ledger cannot be recovered.

**Three operating-discipline rules that only existed inside one skill each.** Both were already stated somewhere and both were found being violated in a session where the skill that stated them was not the one running - which is the argument for `para-shared/operating-discipline.md` existing at all. **Entity creation** now says never to build a project, area, idea or contact folder by hand, whatever shape the request arrives in. `/para-triage`'s `filing.md` had said this for a triaged loose file, but still offered "create the new folder directly" as an equal-weight alternative in two edge cases, and the rule lived nowhere a non-triage request would ever reach: a plain-language ask with no skill invoked - *"migrate the relevant content from my older vault"* - produced three projects and two contacts built by a migration script, none of them through `/para-new`, none of them carrying the scaffold. The three `filing.md` branches now route to `/para-new` rather than offering a hand-built stub beside it. **Fetching template content** generalizes `/para-upgrade`'s existing refusal to fetch a template over the network and act on its contents, which was correct and fired only while `/para-upgrade` was the skill running. In an onboarding session an agent asked to install an integration referenced a local clone path that did not exist on that machine, was blocked four times by the permission classifier, and worked around it with `WebFetch` against the live GitHub repo, writing what came back straight into `resources/scripts/`. The classifier was doing its job; the fallback that got past it is the violation, and it turned out safe only because the fetched file happened to match upstream. The rule now covers any mid-session template install, with the corollary spelled out: no local clone on this machine means stop and route the request to whoever has one, never fetch-and-write as a substitute. Reaction: re-sync installed skill copies, both global installs and any vault-bundled `.claude/skills/`. A vault bundling its own copy is exactly the case that matters here - it shadows the global install, so a team reading the bundled copy keeps the gap until it is replaced.

**`/para-archive` re-depths the links inside whatever it moved.** `/para-new`'s `promote.md` was given this step when idea-to-project promotion shipped; `/para-archive` performs the same kind of move and never got it, so its three link steps are all about references *to* the entity and none about the relative links written *from* inside it. Those break silently on any move that changes the folder's depth, they never appear in the inbound scan by construction, and the archive-hygiene bar the skill enforces reports clean while they dangle. The 2026.08.02 close-out needed twelve such re-depths, all done by hand. The invariant itself moves to `para-shared/operating-discipline.md` as **Moving an entity folder**, since `/para-new` and `/para-archive` were the second and third places to need it and the next skill that moves a folder would have been the fourth. It is stated as a shift per level - add one `../` per level gained, remove one per lost - never as a literal prefix swap, because `../../` also occurs *inside* `../../../` and a search-and-replace that fixes a file at the folder root corrupts one in its `sources/`. Step 7 links to that rule and keeps only the direction table its own four moves need, since two of them change depth and in opposite ways. Archiving an idea and routing a file out of a project both change nothing, and applying a shift to those is as broken as skipping one that was needed. Step 8 verifies both directions and the report counts them separately, since they come from different scans. Reaction: none in vault files. Re-sync installed skill copies, and if a past archive run left outbound links behind, `/para-deep-clean`'s dangling-link audit is what finds them.

**Integrations.** Updated: `outlook` to 2026.09.01 - full message bodies on filing (both orderings of them, reply and forward), a per-keyword `subject_only_keywords` opt-out from body matching, and a multi-mailbox vault syncs what this machine has instead of exiting. `granola` to 2026.09.01 - `"."` as a route target, this vault addressed by path, and a warning where an unresolvable target used to be silent. Unchanged: `activity` stays at 2026.08.03; its fix is in the install snippet, not the script. Reaction: both updated integrations re-sync by straight file copy, with the `"."` route edit granola notes above.

## 2026.08.03

Sixteen changes.

**A checkbox is the actionable frontier.** New `### The actionable frontier` under `## Actions`: a checkbox is a commitment you could act on now or on its marked date, never a plan - when work decomposes into phases, only the unblocked steps carry checkboxes, and everything gated on an unfinished predecessor stays prose (a `## Backlog` heading in the same file, or the brief) until its gate opens. Decompose every plan up front and the speculative items outnumber the committed work until the operator stops believing the count. Two guardrails ship with it: appending to a file already at 12+ open items gets flagged instead of silently done, and triage adds at most one next step per thread, never a decomposition. Detection lives in `/para-daily-brief` (health flags), enforcement at the point of entry in `/para-triage`, repair in `/para-deep-clean`'s new action-grooming step (demote to prose verbatim, close, or date; aspirational dates - overdue 30+ days with no real-world anchor - get stripped rather than left to shout). Reaction: one grooming pass per vault, via `/para-deep-clean` Phase 3 - expect over-threshold files to shed most of their checkboxes into `## Backlog` prose, and falsely-overdue items to lose their invented dates.

**The daily brief leads with vault state, not a task list.** `/para-daily-brief` rebuilt: the default view opens with a per-entity dashboard (open / overdue / undated bars, contact files aggregated to one `network` row), then an Agenda, a Now list capped at five (five ranked beats ten unranked), one-line Later counts, the standing health flags, an ideas lane with 6-month dormancy flags, and triage - closing with exactly one concrete next action instead of a summary. The undated mass that the old brief hid behind a count line is now the structure of the picture. Both skills now also read the fixed root-README shape that 2026.08.02 bought: the brief ranks ties and picks its closing action against `## Vision`, and `/para-triage` makes its in/out call on connector items from `## Operating model`. **A Microsoft 365 mailbox can be synced alongside the personal ones.** `outlook_sync.py` read one `client_id` and one `authority` from the top of the secret file and used them for every account. Both settings now resolve **per account** - `accounts.<email>.client_id` and `accounts.<email>.authority`, each falling back independently to the machine-wide value - so the personal mailboxes keep the shared app while a work mailbox points at its own tenant's registration. They resolve independently on purpose: a mailbox on a shared multi-tenant app needs only the authority switched, and coupling the two would quietly send it at the wrong app. `login` takes `--client-id` and `--authority` to seed them on first run, and `accounts` now prints the authority when it differs from the machine-wide one, because a work mailbox falling back to the personal app is otherwise invisible until the token fails with an error that reads like an expired login. Reaction: none. An account with no overrides resolves exactly as before, so every existing config is unchanged in behaviour.

**Content has a frontier too, and `/para-deep-clean` now prunes against it.** New `### The content frontier` under `## Actions`, the prose half of the actionable-frontier rule shipped above it. Files only ever grow - a development log gets one more dated entry, a fact gets restated in a second file "for context", a superseded decision is left in place because deleting it feels lossy - and nothing in the structure pushes back, so a vault fills with text that costs a session tokens to read and returns nothing. Content inflation is worse than its action sibling in one respect: an over-grown action file announces itself with a count, while an over-grown brief just looks thorough. Three rules: **say it once** (every fact has one owning file, elsewhere it is a link - a copy is a second thing to keep true), **a development log records decisions, not activity**, and **superseded content leaves the live buckets** for `archive/` or git. Detection is a new `/para-daily-brief` health flag (a `brief.md` past 500 lines, counted with `wc -l`, never by reading it); repair is `/para-deep-clean`'s new Step 3.5, which reports duplicated facts, superseded sections, activity-log runs, and orphans nothing links to. **Nothing is ever deleted to satisfy this rule.** Pruning is proposed one item at a time with its text shown, the default disposition is *move* or *demote* rather than remove, a file is never called a duplicate without a content diff against the copy that survives, and `triage/`, every `sources/` folder, and `archive/` are out of scope entirely. Reaction: none in vault files - run `/para-deep-clean` when a brief starts getting flagged.

**A vault ships with a `.gitignore`.** The skeleton shipped none, and the reason one is needed is not obvious: a machine-wide gitignore that hides `CLAUDE.md` and `.claude/` - a common setup for anyone keeping agent config out of client repos - hides them in the vault too, and a vault whose conventions file is untracked loses the one thing its history is for. `base/.gitignore` now ships the canonical file: the override negations, `__pycache__/` + `*.pyc`, and a defensive secret guard in **two scopes** - narrow globs vault-wide (`**/cookies.json`, `**/cookies.txt`, `**/config.json`, `**/.env`) plus the broad `resources/scripts/**/*cookie*` scoped to where only code lives. The two scopes are not redundant: broad vault-wide would hide an event photo named `cookies.jpg`, and narrow-only misses `session-cookie.txt`, which is exactly the shape a scraper writes. The readonly-ipad skeleton ships its own, adding Drive-for-Desktop noise. Reaction: adopt the shipped file if the vault has none, or diff it against yours and take the secret guard.

**The `/para-upgrade` drift check reads content, not the marker string.** Phase 3 compared the `para-os-integration: <name> <revision>` header against the master's and reported from that, so a copy whose marker was bumped by hand while the code stayed old reported clean **permanently**. Reaction: none by hand - the next `/para-upgrade` run reports more than it used to.

**Both shipped integrations now follow one rule: nothing vault-specific in the script.** `granola-sync.js` held its routing table in the body as `const ROUTE = {...}`, which the master ships empty. That made byte-equality impossible, and re-syncing a copy a hand-merge with a silent failure mode: copying the master over an installed copy zeroed the table *and*, because `MULTI` is derived from it, dropped the script out of multi-vault mode - a two-line diff with a total behaviour change. The table moves to a `granola.config.json` beside the script (a `.template` ships as a starting point). **The readonly-ipad render pipeline is reconciled, and its README ends differently.** The three pipeline scripts carried no marker, so the drift check had never once looked at them - which is how they became the worst-synced files in the fleet: `render.mjs` was *ahead* of the master in every installed copy, `render.ps1` one line behind, `flip.ps1` differing only in personalized doc comments. All three are now stamped. The feature that was ahead is upstreamed: a **render-vintage footer**, one timestamp per batch emitted on every PDF, so two documents rendered in the same run carry the same `Updated:` value and a reader who only ever sees PDFs can tell at a glance whether they are the same vintage (`displayHeaderFooter` on, Chromium's default header suppressed, bottom margin 0.6cm → 1cm to make room). `render.ps1` also gains one encoding line: Windows PowerShell 5.1 pipes native-command input as ASCII, so every non-ASCII character in a job path reached `render.mjs` as `?` and the file failed with ENOENT, which made one typographic apostrophe in a filename enough to break a render for anyone not on PowerShell 7. Reaction: re-sync the three pipeline scripts by straight copy, then re-render (`README.pdf` changes, and every PDF gains the footer).

**The outlook filter is per mailbox, and the tool is renamed.** Four faults, all surfaced by the integration's first install against a Microsoft 365 work tenant rather than a personal mailbox. **`keywords` was read once per vault** and applied to every mailbox feeding it - fine while every vault was fed by one personal inbox, useless when a dedicated 3-message engagement mailbox and a shared `info@` funnel of 150-200k messages feed the same `triage/`. `accounts` may now be an object keyed by address, each entry overriding `keywords`, `match_all` and `match_body`, each falling back **independently** to the vault-level default so a block that only tightens keywords keeps the vault's other choices. The list form still works untouched. **There was no catch-all, and the obvious guess did the opposite**: emptying `keywords` leaves the contact allowlist as the only gate, which is stricter, not looser - so `"match_all": true` is now explicit, and it is the natural setting both for a dedicated mailbox and for calibrating a new one. **The filter was subject-only**, a systematic blind spot rather than bad luck: it drops any message whose subject is in a language the filter wasn't written in, and leaves no trace, since a dropped message is invisible by construction. Keywords now match `bodyPreview` as well as the subject, `match_body` defaulting to **true**; set it false for the old behaviour. **And the name was wrong**: `sync` is one of five subcommands, and "outlook_sync.py" led to the reasonable assumption that the keyword filter also constrained `search`, which it never did - `search` queries the whole mailbox by design. The script is now `outlook.py` and its config `outlook.config.json` (deliberately *not* `outlook.json`: that is the machine-global secret, and two files sharing one name across opposite trust zones is how a credential ends up inside a synced vault). Reaction, and it is the largest in this revision: rename the installed script and its config in each vault. The old config name is still read, with a notice, so a half-done migration is loud rather than silent - but **the filter gets looser** the moment you re-sync, because body matching is on by default. Run `sync` without `--write` once and look at what it now catches before trusting it. Shipped guidance worth applying while you are there: a drafted filter is a hypothesis until it has run against real traffic, and company-name keywords match nearly everything in that company's own mailbox, so they are noise dressed as precision.

**Google-native files get normalised at the triage boundary.** A `.gdoc` / `.gsheet` / `.gslides` on a Drive-synced disk is a pointer stub, not a document: the bytes live on a server, and every local read path fails with an I/O error - `Read`, `cat`, `cp`, `Get-Content`, `type`, Python `open`. The vault rule has long been that such a file must be converted to a real one; what was missing was the step that enforces it on the way in. `/para-triage` Step 3 gains a Google-native branch that exports the document through the Drive API and writes a real `.md` sibling into `triage/`, after which it flows through the existing steps as an ordinary loose file. Explicitly *not* the locked-PDF treatment of inferring from the filename: the content is fully readable through the API, so name-only inference would discard a document you can actually read. Three things ship with it. A **`drive` source type** in `## Triage sources`, whose Endpoint is the drive id, because an unscoped Drive query answers "No files found" while the document sits in the folder - a **false quiet**, and on an unattended run that is a scanner reporting all-clear while items pile up, so it is a Strict rule rather than a step detail. A **conversion ledger** at `~/.paraos/cache/triage-drive/<vault>.json`, keyed on file id *plus* `modifiedTime` so an edited document re-converts and an untouched one never does. And a **`convert` argument**: normalise formats, write the ledger, report - no classify, no move, no file, no delete. Filing is judgement and moving or deleting is structural, so an unattended run is a strictly narrower job than the interactive one, not the same job with the prompts turned off. Deleting the converted stub stays a human-approved row, deliberately: `Delete` covers three different cases in this skill, one of them a content-overlap judgement the skill already flags for confirmation, so no flag could safely skip the prompt for stubs alone. Reaction: only a Drive-synced vault needs anything - add a `drive` row with your drive id. `.gdoc` cannot occur on any other substrate.

**Every skill is a loader spine plus `references/`.** A `SKILL.md` is a loader spec, not a prompt: frontmatter sits in context every turn, the body loads on invoke, and a reference loads only when the step needing it runs. A monolithic body therefore charges every invocation for procedure it may never reach. Each skill now keeps its contract, arguments, step sequence and strict rules in the spine and moves the per-step detail out: `/para-triage` to `sources.md` / `filing.md` / `execute.md`, `/para-daily-brief` to `task-scan.md` / `signals.md` / `output.md`, `/para-deep-clean` to one file per phase, `/para-upgrade` to `rules-and-skeleton.md` / `derived-copies.md` / `content-violations.md`, `/para-archive` to `reconcile.md` / `move.md`. Nothing about invocation changes: the split itself touches no frontmatter (the rebuilt brief and the grooming entries above carry their own), and `/para-daily-brief`'s `dashboard.md` stays a root sidecar. The cross-skill rules move with them. `shared/` is renamed **`para-shared/`**, because it installs beside the skills in `~/.claude/skills/`, where a folder called `shared` belongs to whoever claimed the name first; the loader ignores it either way, having no `SKILL.md`. Every file-mutating skill now inherits it in **one line** rather than restating it: `/para-triage` linked to it nowhere and re-stated four of its rules, `/para-upgrade` linked only from a reference file while its spine carried three, and four skills declared the inheritance twice. Two rules duplicated between `/para-triage` and `/para-deep-clean` - no content modification beyond rotating a scan, no translating a document name - move up into the shared file, which no longer names its dependants, since that list is precisely what had gone stale. `/para-daily-brief` inherits nothing and should not: it is read-only by contract. One real defect surfaced in the split and is fixed with it: `/para-daily-brief` counted `triage/.gitkeep` as a loose file, so every clean vault reported one item to process, forever. Reaction: none in vault files - re-sync installed skill copies (global installs and any vault-bundled `.claude/skills/`), copying **the whole skill folder** rather than the `SKILL.md` alone, which now carries only half the procedure.

**A skill creates entities, so a vault stops being started by hand.** Five skills covered every lifecycle transition except the first one: `/para-triage` files an artifact into an entity that already exists, `/para-archive` closes one, `/para-deep-clean` audits them, and nothing created one. The only project creation in the product was `bootstrap-prompt.md`'s hardcoded `vault-setup`, and `/para-archive` carried an edge case that recognised a promotion and then dead-ended on it - "this skill archives, it doesn't promote" - with nowhere to hand off to. **`/para-new`** fills the gap for the four shapes PARA has, a project, an area, an idea or a contact, plus the one promotion the lifecycle defines (`resources/ideas/<name>/` to `projects/<name>/`, which is a move: the brief retenses in place and inbound links repoint in the same pass). Its first job is **classification, not scaffolding**. The sorting test runs before any question about the work, a declared shape does not skip it (`project <name>` states an intent, not a fact), and **the deadline is the discriminator**: no real-world date and it is an idea, whatever the request called it. Recognising an **area** is a first-class outcome rather than a refusal: the request that says "project" and means "something we now maintain" gets an area, and the dated push inside it gets a project alongside, which is the pairing `### Lifecycle` already describes. One rule guards the bucket that mistake fills - an area **absorbs before it multiplies**: assets that gate each other are one area, not several, so the skill checks whether an existing area should widen before it creates a sibling. Two shipped rules constrain the rest. The interview is capped at three questions for a project and two for an area, an idea or a contact, following the bootstrap prompt's rule for the same audience ("exactly these three questions, nothing more - keep it short, I'm new to this"), and a question whose answer lands in no file is not asked. And a new project or area gets **one** unblocked next step, never a decomposition: anything else the operator volunteers is kept verbatim as `## Backlog` prose, per the actionable frontier shipped above. Reaction: one line in `CLAUDE.md` - `### Lifecycle` gains a creation bullet naming the skill and the four shapes, beside the archive bullet that already named `/para-archive`. Then re-sync installed skill copies (global installs and any vault-bundled `.claude/skills/`), copying the whole skill folder.

**A vault can say who writes it, and one rule changes meaning rather than being added.** New optional `## Who writes this vault` section, for the vault several people edit at once - the shape the product now meets every time a client team gets access, and the one it said nothing about. Very little breaks on contact: files sync, `/para-new` already fuzzy-matches a name before creating anything, and the activity ledger above already writes one file per session per person for exactly this reason. What breaks is the register. Every rule the template writes in the first person resolves against one operator and stops resolving the moment four people read the same file. The section carries the roster as a table of person and lane, and five rules with it. **Identity comes from outside the vault**, because a shared file can never say who is running the session: the machine's user or the person's own global config answers that, and where it cannot be answered the agent asks rather than assumes. **An area is the ownership unit** - individual responsibility lives in `areas/`, not in a fork of the vault and not in a per-person folder, which is the answer to the question every team asks first. **Contact files carry no checkboxes**, the one rule here that changes rather than adds: a contact file is named after a person, so a checkbox inside it reads as *that person's* action when it means an action *about* them, an inference a project's `actions.md` never invites. Commitments move to `projects/` and `areas/`, where the actionable frontier already governs them, and `## Next actions` in a contact file stays a prose record of open threads. **The team is not the network**, which `areas/network/` otherwise quietly makes them. And **one stated convention for two people saving one file at once**, the only real failure mode, since the sync client resolves it as last-writer-wins or a conflict copy and neither announces itself.

Two things it deliberately is not. **Not an owner field on projects, areas and ideas**, which is the obvious design and the wrong one: an idea carries no status field by rule, the folder being the only state it has; nothing in the product reads such a field, so it would go stale in the way this revision spent itself fighting elsewhere; and it solves none of the three real frictions, which are whose checkbox this is, two people saving one file, and the same work started twice. **And not an assignment marker.** Attributing an individual checkbox is the change that would genuinely pay, and it is not designed here, because a marker syntax invented before a team has actually collided is a guess. The readonly-ipad flavor needed no change either: its equivalent bullet already says *narrate* rather than *track actions*, since that flavor ships no `actions.md` at all - which is the same conclusion reached from the other end. Reaction: for a vault one person writes, three bullets gain a clause pointing at a section that vault will never have, and nothing else changes. A vault several people write adds the section, fills the roster, and moves any checkbox sitting in a contact file out to the project or area that owns the work.

**A vault can name the code repos it steers.** New optional `## Code repos` section in `bootstrap-prompt.md`'s list, for the adopter whose vault sits above several repositories rather than beside one - the shape para-os is most often put to after the first vault, and the one it said nothing about. Left undeclared, the relationship between the two halves is carried entirely in the operator's head, and the vault's briefs quietly become the only place an implementation plan lives, which is the wrong file for it: a plan belongs with the code it was built from, where the next session on that repo will actually read it. Three rules ship with the section. The linkage is **one-way** - the vault names repos, a repo never names the vault - because repos push to shared remotes, so a vault path inside one is a privacy leak that travels; direction is the fix, not a naming convention. **One system is source of truth per artifact**, everything else holds a copy or a link, which extends `## Authoritative sources` from data to the vault-and-repo boundary, where the same failure looks like a brief and a `CLAUDE.md` disagreeing about how something works and no rule saying which wins. And **intent and design stay in the vault, the implementation plan lives with the code**, with the vault linking the commit rather than restating it. Reaction: none. Add the section only if this vault steers repos, and only once it does.

**A vault can record how it is used, and a skill reads the record.** New opt-in `activity` integration plus `/para-activity-review`. Git says what changed in a vault; neither it nor a sync client's version history says what someone **asked for**, which capability they never found, or where a session stalled - and those are the only questions that improve the product rather than the contents. The ledger is a Claude Code hook: one JSONL line per event into `resources/logs/sessions/`, one file per session because several people syncing one folder cannot share an append target. It fails open and always exits 0, because a hook that can fail is a hook that can stop someone working. Three things it refuses to record, each closing a way this could become surveillance: `tool_response` (it carries file contents), everything after the first token of a Bash command (a command line is where a credential gets pasted), and anything from an unrecognised tool's arguments (an MCP call can hold a mail body). A skill or subagent name is kept, because that is the signal the review reads and it is metadata of the same kind as the tool name; a prompt that opens with a slash command keeps that command even when prompt recording is switched off, since a slash command is expanded rather than issued as a tool call and would otherwise leave no trace at all. The full session transcript is never read, though every event names its path. `/para-activity-review` turns the log into a short ranked list of changes to make, checked against the reviewed vault's own CLAUDE.md, with three rules that decide whether it is useful or corrosive: absence is the primary signal so capabilities are enumerated *before* the log is read, every finding names a defect rather than a person, and every finding carries the change it implies or gets cut. **Opt-in on purpose, and not in `base/`:** no vault gets this by bootstrapping, and a knowledge vault that quietly logged its readers would be a worse product than one with no telemetry at all. Reaction: none. Install it in a vault whose users have been told, and nowhere else.

**Integrations.** New: `activity/` - the vault's own use recorded as JSONL for `/para-activity-review` to read, opt-in and never bootstrapped, Python 3.9+, any platform. Updated: `outlook` to 2026.08.03 - per-account `client_id` / `authority` and filters as above, plus the two `login` flags and the rename. `granola` to 2026.08.03 - the routing table moves out of the script into `granola.config.json`, and the script is renamed `granola-sync.js` -> `granola.js`. **Where a checkbox may live.** New `## Actions` section carrying the bucket table: `projects/` and `areas/` hold open and closed items, `archive/` holds closed ones only, and **`resources/` may never hold a checkbox** - one there is always a filing error. `/para-daily-brief` now discards `resources/` paths outright. Vaults that kept `actions.md` files under `resources/ideas/` must fold those items into each `brief.md` before the work goes invisible.

**An `actions.md` archives with its entity.** Replaces the old "never archive an `actions.md`" rule, which contradicted what `/para-archive` actually does. It archives fully closed; one open `- [ ]` means the entity was archived too early.

**The PARA sorting test, and `### Lifecycle`.** *Committed and dated → project. Maintained, no end date → area. Only thinking about it → idea. Over → archive.* A rolling improvement backlog on something you own is an area wearing a project name. Expect existing `projects/` folders to fail this test: a brief whose own status line reads "Active" or "Ongoing maintenance" is describing an area.

**`📅` means a real-world deadline, never an aspiration.** A decision with an invented date is still a deliberation, and the fake date only makes it surface as falsely overdue.

**Skeleton files an older vault may lack.** `resources/scripts/README.md` (the `PARAOS_HOME` resolver snippet plus a table of installed scripts) and `.claude/settings.json` (`autoMemoryEnabled: false`). The settings file is for adopters with no user-level Claude settings; a vault whose user-level settings already set the same keys should not carry a redundant copy.

**Section renames and de-bloat.** `## Filing rules` → `## Filing and naming`, with task markers folded in under `## Actions`. Memory and File formats condensed. `## Integration scripts and their state` shrinks to a pointer: its state buckets, `PARAOS_HOME` resolver, and language preference now live in `resources/scripts/README.md` (above), read when a script is touched rather than every session. Only the secret-never-inside-the-vault rule stays in `CLAUDE.md`.

Also in this revision, both housekeeping rather than migration work:

- **`triage/` never holds a `README.md`.** Every file there is by definition unprocessed, so a permanent one is indistinguishable from a real item and inflates the loose-file count forever. The skeleton ships `.gitkeep` instead. Delete any `triage/README.md` an earlier skeleton left behind.
- **Two machine-read markers at the top of `CLAUDE.md`**: the `<!-- para-os-template: -->` comment above, and a `**Type:**` line for your own tooling to key off. Both must survive every upgrade.
