# Changelog

Template revisions. Each vault's `CLAUDE.md` carries the revision it was last aligned to, as an HTML comment on line 3:

```
<!-- para-os-template: 2026.08.01 -->
```

`/para-upgrade` reads that marker, compares it against the master's, and applies every entry below after the vault's marker, up to and including the master's. A vault with **no marker** predates the scheme: treat it as pre-2026.08.01 and run the full 2026.08.01 entry against it.

Revisions are dated `YYYY.MM.NN`, not semver: the year and month it shipped, then a zero-padded sequence for the nth revision of that month. The sequence counts, it doesn't grade - `2026.08.02` is not a patch on `2026.08.01`, only the one after it. A revision marks "the template changed in a way an existing vault has to react to"; wording tweaks that change no rule don't get one. Every comparison in the scheme is a plain string compare, which is what the padding is for.

**One legacy label.** The first revision shipped as `2026.08`, before the sequence existed, and was renumbered to `2026.08.01` in `2026.08.02`. A vault still stamped `2026.08` is already on `2026.08.01`: read it as that label, collect the entries after it, and restamp it. Never re-run the `2026.08.01` entry against it.

Installed [integration](integrations/) scripts share the scheme. Each shipped script carries its own marker in its header, stamped with the revision that script last changed in:

```
para-os-integration: granola 2026.08.02
```

An entry's **Integrations** line says which ones moved and why. That marker is read per script, independently of the vault's template marker, so a vault already on the current revision can still be told its installed copy is behind.

**The activity ledger now records what a script wrote and what a session did.** `activity.py` gains two fields. `touched` lists the vault files whose mtime moved while a tool ran, for tools that neither name their own path (`Write`, `Edit`) nor are unable to write (`Read`, `Grep`, ...), capped at `touched_max_files` with the uncapped count in `touched_total`. Without it a script run through Bash left no trace beyond its interpreter's name, and in one real vault 52 of 63 changed files had no write event anywhere. It is inferred, not observed: its window is the tool's duration plus `touched_slack_ms`, so a file another person's sync client landed in that window is indistinguishable from one this call wrote, and `/para-activity-review` is told never to name a person as the author of a `touched` path. `SessionEnd` gains a `summary` object (`prompts` per `prompt_id`, `tools`, `writes` with `touched` counted, `failures`, `denials`, `duration_s`, `last_prompt_tools`), because `reason` belongs to the harness and a client may report `other` for every ending. `summary.prompts: 0` separates sessions nobody typed into, which in one real vault were 72% of the files, from sessions anyone worked in. Both fields are opt-out (`record_touched`, `record_summary`); nothing backfills an older ledger, and the skill's `signals.md` describes such a window as blind rather than quiet. Reaction: re-sync `activity.py` and restamp its marker; re-sync installed `/para-activity-review` copies.

**Every triage file the outlook connector has ever written is a 255-character preview, not the mail.** `fetch_messages` and `search_messages` selected `bodyPreview`, and `write_triage` wrote that straight into the file. Filing now calls a new `fetch_body()`: a single-message `GET /me/messages/{id}?$select=body,uniqueBody` with `Prefer: outlook.body-content-type="text"`, so Graph does the HTML-to-text conversion server-side and nothing here parses HTML. `uniqueBody` first - the reply *without* the quoted history, so the fifth message in a thread is not five copies of the thread - with `body` as the fallback when Graph cannot work out the boundary and `bodyPreview` as the last resort, and a failed fetch warns and falls back rather than killing the sync. Deliberately a second round trip rather than another `$select` on the collection: `uniqueBody` is not returned on collection queries at all, and `body` on a collection would drag whole quoted threads through every page of a sync for messages that mostly will not pass the filter. The reply half is deliberately not enumerated: any non-forward token is stepped over, so `AW:` or `Antw:` on top of a forward needs no list to handle. ## 2026.08.03

Sixteen changes.

**A checkbox is the actionable frontier.** New `### The actionable frontier` under `## Actions`: a checkbox is a commitment you could act on now or on its marked date, never a plan - when work decomposes into phases, only the unblocked steps carry checkboxes, and everything gated on an unfinished predecessor stays prose (a `## Backlog` heading in the same file, or the brief) until its gate opens. Decompose every plan up front and the speculative items outnumber the committed work until the operator stops believing the count. Two guardrails ship with it: appending to a file already at 12+ open items gets flagged instead of silently done, and triage adds at most one next step per thread, never a decomposition. Detection lives in `/para-daily-brief` (health flags), enforcement at the point of entry in `/para-triage`, repair in `/para-deep-clean`'s new action-grooming step (demote to prose verbatim, close, or date; aspirational dates - overdue 30+ days with no real-world anchor - get stripped rather than left to shout). Reaction: one grooming pass per vault, via `/para-deep-clean` Phase 3 - expect over-threshold files to shed most of their checkboxes into `## Backlog` prose, and falsely-overdue items to lose their invented dates.

**The daily brief leads with vault state, not a task list.** `/para-daily-brief` rebuilt: the default view opens with a per-entity dashboard (open / overdue / undated bars, contact files aggregated to one `network` row), then an Agenda, a Now list capped at five (five ranked beats ten unranked), one-line Later counts, the standing health flags, an ideas lane with 6-month dormancy flags, and triage - closing with exactly one concrete next action instead of a summary. The undated mass that the old brief hid behind a count line is now the structure of the picture. Both skills now also read the fixed root-README shape that 2026.08.02 bought: the brief ranks ties and picks its closing action against `## Vision`, and `/para-triage` makes its in/out call on connector items from `## Operating model`. On harnesses with an Artifact tool, the default run additionally publishes a self-contained HTML dashboard (page spec in the skill's `dashboard.md` sidecar), updated in place across days and skipped silently where unsupported. Full task expansion stays behind `all`; `today` / `week` / `overdue` keep their meanings. Reaction: none in vault files - re-sync installed skill copies (global installs and any vault-bundled `.claude/skills/`).

**A vault can declare `## Agenda sources`.** The Triage-sources pattern applied to calendars: an optional CLAUDE.md table (`connector:` rows only, read-only, the calendar account as Endpoint) that gives `/para-daily-brief`'s 🗓 Agenda a live calendar. Before this, the Agenda read only a hand-kept root `meetings.md` - which vaults with a connector-reachable calendar never keep, so their briefs opened with no agenda at all, which is a poor start for a morning ritual. `meetings.md` stays the fallback for vaults whose calendar no connector reaches, and merges when both exist. Declared once in `bootstrap-prompt.md`'s optional-sections list, per the no-restatement rule. Reaction: add the block only in vaults whose calendar a connector can actually reach; everyone else changes nothing.

**A Microsoft 365 mailbox can be synced alongside the personal ones.** `outlook_sync.py` read one `client_id` and one `authority` from the top of the secret file and used them for every account. That holds only while every mailbox is a personal one: a personal-accounts app is registered against the `consumers` authority, which refuses work and school accounts outright, so a Microsoft 365 mailbox could not be added at all without re-registering the shared app and re-consenting every existing login. Both settings now resolve **per account** - `accounts.<email>.client_id` and `accounts.<email>.authority`, each falling back independently to the machine-wide value - so the personal mailboxes keep the shared app while a work mailbox points at its own tenant's registration. They resolve independently on purpose: a mailbox on a shared multi-tenant app needs only the authority switched, and coupling the two would quietly send it at the wrong app. `login` takes `--client-id` and `--authority` to seed them on first run, and `accounts` now prints the authority when it differs from the machine-wide one, because a work mailbox falling back to the personal app is otherwise invisible until the token fails with an error that reads like an expired login. Reaction: none. An account with no overrides resolves exactly as before, so every existing config is unchanged in behaviour.

**Content has a frontier too, and `/para-deep-clean` now prunes against it.** New `### The content frontier` under `## Actions`, the prose half of the actionable-frontier rule shipped above it. Files only ever grow - a development log gets one more dated entry, a fact gets restated in a second file "for context", a superseded decision is left in place because deleting it feels lossy - and nothing in the structure pushes back, so a vault fills with text that costs a session tokens to read and returns nothing. Content inflation is worse than its action sibling in one respect: an over-grown action file announces itself with a count, while an over-grown brief just looks thorough. Three rules: **say it once** (every fact has one owning file, elsewhere it is a link - a copy is a second thing to keep true), **a development log records decisions, not activity**, and **superseded content leaves the live buckets** for `archive/` or git. Detection is a new `/para-daily-brief` health flag (a `brief.md` past 500 lines, counted with `wc -l`, never by reading it); repair is `/para-deep-clean`'s new Step 3.5, which reports duplicated facts, superseded sections, activity-log runs, and orphans nothing links to. **Nothing is ever deleted to satisfy this rule.** Pruning is proposed one item at a time with its text shown, the default disposition is *move* or *demote* rather than remove, a file is never called a duplicate without a content diff against the copy that survives, and `triage/`, every `sources/` folder, and `archive/` are out of scope entirely. Reaction: none in vault files - run `/para-deep-clean` when a brief starts getting flagged.

**A vault ships with a `.gitignore`.** The skeleton shipped none, and the reason one is needed is not obvious: a machine-wide gitignore that hides `CLAUDE.md` and `.claude/` - a common setup for anyone keeping agent config out of client repos - hides them in the vault too, and a vault whose conventions file is untracked loses the one thing its history is for. `base/.gitignore` now ships the canonical file: the override negations, `__pycache__/` + `*.pyc`, and a defensive secret guard in **two scopes** - narrow globs vault-wide (`**/cookies.json`, `**/cookies.txt`, `**/config.json`, `**/.env`) plus the broad `resources/scripts/**/*cookie*` scoped to where only code lives. The two scopes are not redundant: broad vault-wide would hide an event photo named `cookies.jpg`, and narrow-only misses `session-cookie.txt`, which is exactly the shape a scraper writes. The readonly-ipad skeleton ships its own, adding Drive-for-Desktop noise. Reaction: adopt the shipped file if the vault has none, or diff it against yours and take the secret guard.

**The `/para-upgrade` drift check reads content, not the marker string.** Phase 3 compared the `para-os-integration: <name> <revision>` header against the master's and reported from that, so a copy whose marker was bumped by hand while the code stayed old reported clean **permanently**. The check now diffs the file against `git show <ref>:<master path>` (line endings normalized first, or a Windows checkout diffs as entirely changed) and reports *identical*, *behind*, *ahead*, *both*, or *marker matches but content differs* from the diff itself; the marker is kept only to identify which integration a file came from. It also greps the **whole vault** rather than `resources/scripts/`, since a flavor installs its scripts elsewhere, and resolves a name through `integrations/<name>/` then `flavors/<name>/pipeline/` - falling back, when the folder resolves but the filename does not, to the folder's single shipped script, so a file renamed upstream reports as a rename rather than as an unresolvable marker. Two blind spots close with it: a vault's **bundled `.claude/skills/`** is now audited as skeleton content (it was the one copy nothing checked, and it shadows the user-level install, so a stale one silently overrides a correct global skill), and the readonly-ipad pipeline scripts finally carry markers. Reaction: none by hand - the next `/para-upgrade` run reports more than it used to.

**Both shipped integrations now follow one rule: nothing vault-specific in the script.** `granola-sync.js` held its routing table in the body as `const ROUTE = {...}`, which the master ships empty. That made byte-equality impossible, and re-syncing a copy a hand-merge with a silent failure mode: copying the master over an installed copy zeroed the table *and*, because `MULTI` is derived from it, dropped the script out of multi-vault mode - a two-line diff with a total behaviour change. The table moves to a `granola.config.json` beside the script (a `.template` ships as a starting point). Both integrations now name that file the same way - `<name>.config.json` beside the script for what syncs with the vault, `~/.paraos/secrets/<name>.json` for what never leaves the machine - and `resources/scripts/README.md` states the pair once, so a third integration cannot invent a third shape. Absent or empty means single-vault mode; a malformed file now **stops the run** instead of falling through to an empty config - and so does one that parses but is the wrong shape (an array, a string), which is exactly as dangerous as malformed JSON and was not caught at first. The script is renamed too: `<integration>.js` beside `<integration>.config.json` is the one shape the naming settles on, the same pairing `outlook.py` and `outlook.config.json` establish below. Reaction: move your `ROUTE` map into a new `granola.config.json` next to the script as `{"route": {...}}`, then re-sync the renamed `granola.js` by straight copy. Until you do, the copy keeps working exactly as it is.

**The readonly-ipad render pipeline is reconciled, and its README ends differently.** The three pipeline scripts carried no marker, so the drift check had never once looked at them - which is how they became the worst-synced files in the fleet: `render.mjs` was *ahead* of the master in every installed copy, `render.ps1` one line behind, `flip.ps1` differing only in personalized doc comments. All three are now stamped. The feature that was ahead is upstreamed: a **render-vintage footer**, one timestamp per batch emitted on every PDF, so two documents rendered in the same run carry the same `Updated:` value and a reader who only ever sees PDFs can tell at a glance whether they are the same vintage (`displayHeaderFooter` on, Chromium's default header suppressed, bottom margin 0.6cm → 1cm to make room). `render.ps1` also gains one encoding line: Windows PowerShell 5.1 pipes native-command input as ASCII, so every non-ASCII character in a job path reached `render.mjs` as `?` and the file failed with ENOENT, which made one typographic apostrophe in a filename enough to break a render for anyone not on PowerShell 7. The flavor also gains its own `README.md.template`, identical to the base except for the closing line: the base line points at `CLAUDE.md` and `/para-daily-brief`, and in this flavor `CLAUDE.md` is on the render denylist while there is no `actions.md` for the brief to read, so both references would be dead ends in a rendered README. Reaction: re-sync the three pipeline scripts by straight copy, then re-render (`README.pdf` changes, and every PDF gains the footer).

**The outlook filter is per mailbox, and the tool is renamed.** Four faults, all surfaced by the integration's first install against a Microsoft 365 work tenant rather than a personal mailbox. **`keywords` was read once per vault** and applied to every mailbox feeding it - fine while every vault was fed by one personal inbox, useless when a dedicated 3-message engagement mailbox and a shared `info@` funnel of 150-200k messages feed the same `triage/`. `accounts` may now be an object keyed by address, each entry overriding `keywords`, `match_all` and `match_body`, each falling back **independently** to the vault-level default so a block that only tightens keywords keeps the vault's other choices. The list form still works untouched. **There was no catch-all, and the obvious guess did the opposite**: emptying `keywords` leaves the contact allowlist as the only gate, which is stricter, not looser - so `"match_all": true` is now explicit, and it is the natural setting both for a dedicated mailbox and for calibrating a new one. **The filter was subject-only**, a systematic blind spot rather than bad luck: it drops any message whose subject is in a language the filter wasn't written in, and leaves no trace, since a dropped message is invisible by construction. Keywords now match `bodyPreview` as well as the subject, `match_body` defaulting to **true**; set it false for the old behaviour. **And the name was wrong**: `sync` is one of five subcommands, and "outlook_sync.py" led to the reasonable assumption that the keyword filter also constrained `search`, which it never did - `search` queries the whole mailbox by design. The script is now `outlook.py` and its config `outlook.config.json` (deliberately *not* `outlook.json`: that is the machine-global secret, and two files sharing one name across opposite trust zones is how a credential ends up inside a synced vault). Reaction, and it is the largest in this revision: rename the installed script and its config in each vault. The old config name is still read, with a notice, so a half-done migration is loud rather than silent - but **the filter gets looser** the moment you re-sync, because body matching is on by default. Run `sync` without `--write` once and look at what it now catches before trusting it. Shipped guidance worth applying while you are there: a drafted filter is a hypothesis until it has run against real traffic, and company-name keywords match nearly everything in that company's own mailbox, so they are noise dressed as precision.

**Google-native files get normalised at the triage boundary.** A `.gdoc` / `.gsheet` / `.gslides` on a Drive-synced disk is a pointer stub, not a document: the bytes live on a server, and every local read path fails with an I/O error - `Read`, `cat`, `cp`, `Get-Content`, `type`, Python `open`. The vault rule has long been that such a file must be converted to a real one; what was missing was the step that enforces it on the way in. `/para-triage` Step 3 gains a Google-native branch that exports the document through the Drive API and writes a real `.md` sibling into `triage/`, after which it flows through the existing steps as an ordinary loose file. Explicitly *not* the locked-PDF treatment of inferring from the filename: the content is fully readable through the API, so name-only inference would discard a document you can actually read. Three things ship with it. A **`drive` source type** in `## Triage sources`, whose Endpoint is the drive id, because an unscoped Drive query answers "No files found" while the document sits in the folder - a **false quiet**, and on an unattended run that is a scanner reporting all-clear while items pile up, so it is a Strict rule rather than a step detail. A **conversion ledger** at `~/.paraos/cache/triage-drive/<vault>.json`, keyed on file id *plus* `modifiedTime` so an edited document re-converts and an untouched one never does. And a **`convert` argument**: normalise formats, write the ledger, report - no classify, no move, no file, no delete. Filing is judgement and moving or deleting is structural, so an unattended run is a strictly narrower job than the interactive one, not the same job with the prompts turned off. Deleting the converted stub stays a human-approved row, deliberately: `Delete` covers three different cases in this skill, one of them a content-overlap judgement the skill already flags for confirmation, so no flag could safely skip the prompt for stubs alone. Reaction: only a Drive-synced vault needs anything - add a `drive` row with your drive id. `.gdoc` cannot occur on any other substrate.

**Every skill is a loader spine plus `references/`.** A `SKILL.md` is a loader spec, not a prompt: frontmatter sits in context every turn, the body loads on invoke, and a reference loads only when the step needing it runs. A monolithic body therefore charges every invocation for procedure it may never reach. Each skill now keeps its contract, arguments, step sequence and strict rules in the spine and moves the per-step detail out: `/para-triage` to `sources.md` / `filing.md` / `execute.md`, `/para-daily-brief` to `task-scan.md` / `signals.md` / `output.md`, `/para-deep-clean` to one file per phase, `/para-upgrade` to `rules-and-skeleton.md` / `derived-copies.md` / `content-violations.md`, `/para-archive` to `reconcile.md` / `move.md`. Across the five that halves what an invocation loads. Nothing about invocation changes: the split itself touches no frontmatter (the rebuilt brief and the grooming entries above carry their own), and `/para-daily-brief`'s `dashboard.md` stays a root sidecar. The cross-skill rules move with them. `shared/` is renamed **`para-shared/`**, because it installs beside the skills in `~/.claude/skills/`, where a folder called `shared` belongs to whoever claimed the name first; the loader ignores it either way, having no `SKILL.md`. Every file-mutating skill now inherits it in **one line** rather than restating it: `/para-triage` linked to it nowhere and re-stated four of its rules, `/para-upgrade` linked only from a reference file while its spine carried three, and four skills declared the inheritance twice. Two rules duplicated between `/para-triage` and `/para-deep-clean` - no content modification beyond rotating a scan, no translating a document name - move up into the shared file, which no longer names its dependants, since that list is precisely what had gone stale. `/para-daily-brief` inherits nothing and should not: it is read-only by contract. One real defect surfaced in the split and is fixed with it: `/para-daily-brief` counted `triage/.gitkeep` as a loose file, so every clean vault reported one item to process, forever. Reaction: none in vault files - re-sync installed skill copies (global installs and any vault-bundled `.claude/skills/`), copying **the whole skill folder** rather than the `SKILL.md` alone, which now carries only half the procedure.

**A skill creates entities, so a vault stops being started by hand.** Five skills covered every lifecycle transition except the first one: `/para-triage` files an artifact into an entity that already exists, `/para-archive` closes one, `/para-deep-clean` audits them, and nothing created one. The only project creation in the product was `bootstrap-prompt.md`'s hardcoded `vault-setup`, and `/para-archive` carried an edge case that recognised a promotion and then dead-ended on it - "this skill archives, it doesn't promote" - with nowhere to hand off to. **`/para-new`** fills the gap for the four shapes PARA has, a project, an area, an idea or a contact, plus the one promotion the lifecycle defines (`resources/ideas/<name>/` to `projects/<name>/`, which is a move: the brief retenses in place and inbound links repoint in the same pass). Its first job is **classification, not scaffolding**. The sorting test runs before any question about the work, a declared shape does not skip it (`project <name>` states an intent, not a fact), and **the deadline is the discriminator**: no real-world date and it is an idea, whatever the request called it. Recognising an **area** is a first-class outcome rather than a refusal: the request that says "project" and means "something we now maintain" gets an area, and the dated push inside it gets a project alongside, which is the pairing `### Lifecycle` already describes. One rule guards the bucket that mistake fills - an area **absorbs before it multiplies**: assets that gate each other are one area, not several, so the skill checks whether an existing area should widen before it creates a sibling. Two shipped rules constrain the rest. The interview is capped at three questions for a project and two for an area, an idea or a contact, following the bootstrap prompt's rule for the same audience ("exactly these three questions, nothing more - keep it short, I'm new to this"), and a question whose answer lands in no file is not asked. And a new project or area gets **one** unblocked next step, never a decomposition: anything else the operator volunteers is kept verbatim as `## Backlog` prose, per the actionable frontier shipped above. Reaction: one line in `CLAUDE.md` - `### Lifecycle` gains a creation bullet naming the skill and the four shapes, beside the archive bullet that already named `/para-archive`. Then re-sync installed skill copies (global installs and any vault-bundled `.claude/skills/`), copying the whole skill folder.

**A vault can say who writes it, and one rule changes meaning rather than being added.** New optional `## Who writes this vault` section, for the vault several people edit at once - the shape the product now meets every time a client team gets access, and the one it said nothing about. Very little breaks on contact: files sync, `/para-new` already fuzzy-matches a name before creating anything, and the activity ledger above already writes one file per session per person for exactly this reason. What breaks is the register. Every rule the template writes in the first person resolves against one operator and stops resolving the moment four people read the same file. The section carries the roster as a table of person and lane, and five rules with it. **Identity comes from outside the vault**, because a shared file can never say who is running the session: the machine's user or the person's own global config answers that, and where it cannot be answered the agent asks rather than assumes. **An area is the ownership unit** - individual responsibility lives in `areas/`, not in a fork of the vault and not in a per-person folder, which is the answer to the question every team asks first. **Contact files carry no checkboxes**, the one rule here that changes rather than adds: a contact file is named after a person, so a checkbox inside it reads as *that person's* action when it means an action *about* them, an inference a project's `actions.md` never invites. Commitments move to `projects/` and `areas/`, where the actionable frontier already governs them, and `## Next actions` in a contact file stays a prose record of open threads. **The team is not the network**, which `areas/network/` otherwise quietly makes them. And **one stated convention for two people saving one file at once**, the only real failure mode, since the sync client resolves it as last-writer-wins or a conflict copy and neither announces itself.

Two things it deliberately is not. **Not an owner field on projects, areas and ideas**, which is the obvious design and the wrong one: an idea carries no status field by rule, the folder being the only state it has; nothing in the product reads such a field, so it would go stale in the way this revision spent itself fighting elsewhere; and it solves none of the three real frictions, which are whose checkbox this is, two people saving one file, and the same work started twice. **And not an assignment marker.** Attributing an individual checkbox is the change that would genuinely pay, and it is not designed here, because a marker syntax invented before a team has actually collided is a guess. The readonly-ipad flavor needed no change either: its equivalent bullet already says *narrate* rather than *track actions*, since that flavor ships no `actions.md` at all - which is the same conclusion reached from the other end. Reaction: for a vault one person writes, three bullets gain a clause pointing at a section that vault will never have, and nothing else changes. A vault several people write adds the section, fills the roster, and moves any checkbox sitting in a contact file out to the project or area that owns the work.

**A vault can name the code repos it steers.** New optional `## Code repos` section in `bootstrap-prompt.md`'s list, for the adopter whose vault sits above several repositories rather than beside one - the shape para-os is most often put to after the first vault, and the one it said nothing about. Left undeclared, the relationship between the two halves is carried entirely in the operator's head, and the vault's briefs quietly become the only place an implementation plan lives, which is the wrong file for it: a plan belongs with the code it was built from, where the next session on that repo will actually read it. Three rules ship with the section. The linkage is **one-way** - the vault names repos, a repo never names the vault - because repos push to shared remotes, so a vault path inside one is a privacy leak that travels; direction is the fix, not a naming convention. **One system is source of truth per artifact**, everything else holds a copy or a link, which extends `## Authoritative sources` from data to the vault-and-repo boundary, where the same failure looks like a brief and a `CLAUDE.md` disagreeing about how something works and no rule saying which wins. And **intent and design stay in the vault, the implementation plan lives with the code**, with the vault linking the commit rather than restating it. Reaction: none. Add the section only if this vault steers repos, and only once it does.

**A vault can record how it is used, and a skill reads the record.** New opt-in `activity` integration plus `/para-activity-review`. Git says what changed in a vault; neither it nor a sync client's version history says what someone **asked for**, which capability they never found, or where a session stalled - and those are the only questions that improve the product rather than the contents. The ledger is a Claude Code hook: one JSONL line per event into `resources/logs/sessions/`, one file per session because several people syncing one folder cannot share an append target. It fails open and always exits 0, because a hook that can fail is a hook that can stop someone working. Three things it refuses to record, each closing a way this could become surveillance: `tool_response` (it carries file contents), everything after the first token of a Bash command (a command line is where a credential gets pasted), and anything from an unrecognised tool's arguments (an MCP call can hold a mail body). A skill or subagent name is kept, because that is the signal the review reads and it is metadata of the same kind as the tool name; a prompt that opens with a slash command keeps that command even when prompt recording is switched off, since a slash command is expanded rather than issued as a tool call and would otherwise leave no trace at all. The full session transcript is never read, though every event names its path. `/para-activity-review` turns the log into a short ranked list of changes to make, checked against the reviewed vault's own CLAUDE.md, with three rules that decide whether it is useful or corrosive: absence is the primary signal so capabilities are enumerated *before* the log is read, every finding names a defect rather than a person, and every finding carries the change it implies or gets cut. **Opt-in on purpose, and not in `base/`:** no vault gets this by bootstrapping, and a knowledge vault that quietly logged its readers would be a worse product than one with no telemetry at all. Reaction: none. Install it in a vault whose users have been told, and nowhere else.

**Integrations.** New: `activity/` - the vault's own use recorded as JSONL for `/para-activity-review` to read, opt-in and never bootstrapped, Python 3.9+, any platform. Updated: `outlook` to 2026.08.03 - per-account `client_id` / `authority` and filters as above, plus the two `login` flags and the rename. `granola` to 2026.08.03 - the routing table moves out of the script into `granola.config.json`, and the script is renamed `granola-sync.js` -> `granola.js`. New marker: `readonly-ipad` at 2026.08.03 - the flavor's three pipeline scripts enter the drift scheme for the first time, resolving under `flavors/readonly-ipad/pipeline/`. Reaction: both integrations now re-sync by straight file copy, with the one-time config migration each notes above.

## 2026.08.02

Four changes.

**Revisions carry a sequence, so a month can hold more than one.** `YYYY.MM` could only ever label one revision per month; the second one in a month had to choose between lying about its date and burning the next month's label. Revisions are now `YYYY.MM.NN`, zero-padded so a plain string compare still orders them (`2026.08.01` < `2026.08.02` < `2026.09.01`), and the sequence carries no severity - it says which one came next, not how big it was. The first revision was renumbered from `2026.08` to `2026.08.01`; this one is `2026.08.02`. Reaction: none by hand. A vault stamped `2026.08` is read as `2026.08.01`, already migrated, and restamped in Phase 5 like any other upgrade.

**Conversation records route by ownership.** A dated conversation record (meeting notes, call transcript, chat or email sequence) owned by a single project or area is a source like any other: it files in that entity's `sources/`, under the vault's source-document naming. `archive/meetings/` narrows to records that span several entities or have no owning entity - the cross-cutting audit trail. The old rule read literally sent every conversational artifact to `archive/meetings/`; this writes down the boundary as practiced. Reaction: move single-owner records out of `archive/meetings/` into the owning entity's `sources/`, renaming to the source-document convention and repointing inbound links in the same pass.

**The root README has one fixed shape and holds no hand-maintained state.** The seed named the opening sections only loosely ("or the vault's equivalent"), so vaults drifted into renamed or translated headings, hand-maintained dashboards duplicating what `projects/*/brief.md` and `actions.md` already hold (stale but still reading as current), and stub Visions. The rule now names the first four `##` headings exactly (`Identity`, `Operating model`, `Track record`, `Vision`), in that order and in English whatever the body language; Vision is the end state and its horizon, never a stub; vault-specific sections follow, with `## Principles` (standing decisions not to relitigate) the one optional section with a fixed name; and the README carries no project status list, deadline table, open-action list, or live status narrative (no checkbox, `📅` marker, or status column), because `/para-daily-brief` is the dashboard. `README.md.template` carries a definition per heading, the bootstrap drafts all four sections and the braindump is not done until Vision is real, and `/para-deep-clean` Phase 1 audits the shape, fixing it in Phase 2 ahead of the entity READMEs. Reaction: rename or translate the headings to the four, fold numbered or renamed opening sections under them (an inventory or brand list becomes a `###` under Track record), write a real Vision, reduce any "Working in this vault" section to the one closing line, and move project, deadline and status tables out of the root README into the owning `brief.md` (status) or `actions.md` (deadlines become `📅` items).

**Integration scripts carry their own revision, and `/para-upgrade` reports drift.** An installed integration is a *copy*: the script lands in `resources/scripts/` on install day and nothing ever told the vault when the master moved. `/para-upgrade` didn't look either - the changelog is its scope, and the changelog never mentioned integrations - so a fixed script stayed broken in any vault that already had it. Every shipped script now carries `para-os-integration: <name> <revision>` in its header, stamped with the revision that script's *code* last changed in, so a README rewording moves nothing, and each entry here notes what moved under an **Integrations** line. `/para-upgrade` Phase 3 compares the marker in each installed copy against the master's at the ref and **reports** the gap; it never overwrites, because these copies are meant to be edited, so a resync is a hand-merge the operator makes with the entry in front of them. The check keys off the script's own marker rather than the vault's template marker, so it runs even on a vault that is already on the current revision. Reaction: one pass over the scripts already installed. Nothing installed before this revision carries a marker, so the first run after it asks, per unmarked script, which shipped integration it is and stamps it at the revision it was installed from; a script that is the vault's own stays unmarked and is named as skipped. From then on the check reports which copies are behind. The one edit is to the vault's own `resources/scripts/README.md`, which gains a paragraph saying what the marker is and that a resync is a hand-merge - it ships in the skeleton, so a vault that already has the file gets the paragraph added to its copy.

**Integrations.** New: `outlook/` - personal Outlook / Hotmail into `triage/` over Graph device-code OAuth, read-only, Python 3.9+, any platform. Updated: `granola` to 2026.08.02 - a character a filename can't hold now becomes a space instead of vanishing, so a meeting titled `Q3/Q4 plan` files as `Q3 Q4 plan` rather than `Q3Q4 plan`, and a meeting with no title files as `untitled` rather than `null`. Reaction: none for meetings already synced, since the dedup ledger keys on the meeting id, not the filename. A meeting whose ledger entry was lost but whose note is still on disk re-files under the new name; delete whichever copy you don't want.

## 2026.08.01

Six changes.

**Where a checkbox may live.** New `## Actions` section carrying the bucket table: `projects/` and `areas/` hold open and closed items, `archive/` holds closed ones only, and **`resources/` may never hold a checkbox** - one there is always a filing error. `/para-daily-brief` now discards `resources/` paths outright. Vaults that kept `actions.md` files under `resources/ideas/` must fold those items into each `brief.md` before the work goes invisible.

**An `actions.md` archives with its entity.** Replaces the old "never archive an `actions.md`" rule, which contradicted what `/para-archive` actually does. It archives fully closed; one open `- [ ]` means the entity was archived too early.

**The PARA sorting test, and `### Lifecycle`.** *Committed and dated → project. Maintained, no end date → area. Only thinking about it → idea. Over → archive.* A rolling improvement backlog on something you own is an area wearing a project name. Expect existing `projects/` folders to fail this test: a brief whose own status line reads "Active" or "Ongoing maintenance" is describing an area.

**`📅` means a real-world deadline, never an aspiration.** A decision with an invented date is still a deliberation, and the fake date only makes it surface as falsely overdue.

**Skeleton files an older vault may lack.** `resources/scripts/README.md` (the `PARAOS_HOME` resolver snippet plus a table of installed scripts) and `.claude/settings.json` (`autoMemoryEnabled: false`). The settings file is for adopters with no user-level Claude settings; a vault whose user-level settings already set the same keys should not carry a redundant copy.

**Section renames and de-bloat.** `## Filing rules` → `## Filing and naming`, with task markers folded in under `## Actions`. Memory and File formats condensed. `## Integration scripts and their state` shrinks to a pointer: its state buckets, `PARAOS_HOME` resolver, and language preference now live in `resources/scripts/README.md` (above), read when a script is touched rather than every session. Only the secret-never-inside-the-vault rule stays in `CLAUDE.md`.

Also in this revision, both housekeeping rather than migration work:

- **`triage/` never holds a `README.md`.** Every file there is by definition unprocessed, so a permanent one is indistinguishable from a real item and inflates the loose-file count forever. The skeleton ships `.gitkeep` instead. Delete any `triage/README.md` an earlier skeleton left behind.
- **Two machine-read markers at the top of `CLAUDE.md`**: the `<!-- para-os-template: -->` comment above, and a `**Type:**` line for your own tooling to key off. Both must survive every upgrade.
